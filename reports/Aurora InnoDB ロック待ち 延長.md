# 120秒は待つ側のベルだけを遅らせる

図書館で本の一行を直すとき、鉛筆を握った人が席を外しても、列のベルを50秒から120秒に遅らせただけでは、その人は早く戻ってこない。Aurora MySQL Serverless v2（コミュニティ MySQL 8.4.7 互換）で `innodb_lock_wait_timeout` を既定の **50秒から120秒**へ上げても、速くなるのはロックを握っている側ではない。変わるのは、InnoDB の行ロックを待っている側が **ERROR 1205** で今の文を諦めるまでの天井だけである。相手が50秒以内にロックを放せば結果は同じで、差が出るのは保持が50秒を超えるときだけだ。デッドロック検出は既定のまま有効なので、輪になった待ちはタイムアウトを待たず **ERROR 1213** でトランザクション全体が戻る。メタデータロック（`lock_wait_timeout`、既定 **31536000秒**）にも効かない。公開の50対120のベンチマークは無く、以下は測定ではなく機構の説明である。50秒を選んだ一次資料も見つかっていない。呼び出し側の既定（ALB の無通信 **60秒**、API Gateway の統合 **29秒**）よりデータベースの待ちが長いと、利用者は先に失敗し、接続だけが残り続ける。

## 図書館の鉛筆は、列のベルだけを遅らせる

昔の貸し出しは、ノートの1ページを直すときも本を一冊まるごとカウンターの奥へしまった。別のページが欲しい人も、その人が書き終わるまで行列に立つだけだった。今のやり方は、直している行だけを一本の鉛筆で押さえる。隣の行は、別の人が同時に直せる。その代わり、鉛筆を持った人が席を外すと、次の人は鉛筆が戻るまで何も書けない。二人が「あなたの鉛筆と、わたしの消しゴム」を取り合う輪なら、係はすぐに見て、書いた量が少ない方の作業をなかったことにする。輪ではなく、ただ席を外しているだけなら、係は鳴らない。列の人を永遠に立たせないためにベルがある。ベルが鳴ると失敗するのは、列の人の「今書こうとしていた一文」だけである。鉛筆を持った人の本は、開いたまま残る。ベルを50秒から120秒にしても、持つ人は速くならない。本の名前や棚を変える目録カードは別のカウンターで、そちらのベルは最長で1年である。120秒にしても、目録の列は動かない。

同じ話を InnoDB の言葉に戻す。MyISAM などの表ロックは、更新できるセッションが一度に一つだけで、他のセッションは「今の変更文が終わるまで」待たされる。InnoDB の行ロックは別の行なら競合が少なく、公式は利点の一つに「1行を長いあいだロックできる」ことを挙げる（[Internal Locking Methods（MySQL 5.7）](https://docs.oracle.com/cd/E17952_01/mysql-5.7-en/internal-locking.html)）。その利点が、待ち人を無限に座らせない秒数を必要にした。`innodb_lock_wait_timeout` は、InnoDB トランザクションが行ロックを待って諦めるまでの秒数で、MySQL 8.4 の既定は **50**、最小 **1**、最大 **1073741824**、単位は秒、スコープは Global と Session、動的変更はできる。`SET_VAR` ヒントは効かない（[MySQL 8.4 innodb_lock_wait_timeout](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_lock_wait_timeout)）。最大値は 2^30 秒で、365.25日の年に直すと約34.0年になる。これはマニュアルの文言ではなく計算であり、50は上限側ではなく短い側の既定である。

デッドロックは待ちグラフの輪である。検出が有効（既定）なら、InnoDB はデッドロックを直ちに見つけ、挿入・更新・削除した行数が小さい方のトランザクションを戻して輪を壊す。このとき `innodb_lock_wait_timeout` は使わない（[Deadlock Detection（8.4）](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlock-detection.html)）。タイムアウトが要るのは輪ではないとき、つまり誰も待たずにロックを持ち続けるトランザクションの後ろに並ぶ列である。検出を切ったとき、および `innodb_table_locks = 1` かつ `autocommit = 0` でなければ見えない `LOCK TABLES` や他エンジンのロックが混ざったとき、その尻ぬぐいもこの秒数である。待ちリスト上のトランザクションが **200** に達したとき、または参照するロックが **1,000,000** を超えるとき、InnoDB はそれをデッドロックとして扱い、探索していた側を戻す。マニュアルはその段落にエラー番号を書いておらず、待っている側をタイムアウトさせるとも書いていない。

経験する待ち時間は、相手がロックを放す時刻と天井の早い方である。全クエリが120秒になるわけではない。相手が30秒で終われば、50でも120でも待ちは30秒である。差が出るのは保持が50秒を超えるときだけだ。保持が50秒より長く120秒以内なら、50では1205になり、120では相手の完了時に成功し得る。保持が120秒を超えるか、持ち手が COMMIT しないなら、両方失敗し、120の方が接続を最大 **70秒**長く占有する。120/50 = **2.4** は天井の算術であり、測定された遅延倍率ではない。50対120を同じ負荷で比べた公開ベンチマークは、この調査では見つかっていない。

タイマーが動くのは、そのロック要求のためにスレッドが停止しているあいだだけである。文の開始から COMMIT までの経過時間ではない。MySQL 8.4 の `lock0wait.cc` は、待ちに入るたびにその時点のタイムアウトをスロットへコピーし、停止時刻からの経過が設定秒数より大きいときだけタイムアウトにする。比較は `>` であり `>=` ではない。判定スレッドは約1秒に1回で、実装コメント自身が「T の次は T か T+0.99 か、誰も気にしない」と書いている（[lock0wait.cc（8.4）](https://raw.githubusercontent.com/mysql/mysql-server/8.4/storage/innobase/lock/lock0wait.cc)）。したがって「ちょうど50.000秒で必ず切れる」ではない。切れるのは設定値より後、おおよそ1秒の解像度である。ブロッカーが判定より前に COMMIT すれば待ちは解けて文は続く。次のロック要求で再び停止すれば、タイマーはやり直す。文がロックを順番に複数回待つと、ブロック時間の合計は設定秒数を超え得る。メタデータロックのマニュアルはこの「試行ごとに別タイマー」を明示するが、InnoDB 側の変数説明にはその文が無い。InnoDB 側はソースからの帰結である。待ちの途中で `SET SESSION` しても、進行中のその待ちの期限はコピー済みの値のまま、と読める。マニュアルは途中変更に触れていない。同じソースには、高優先度トランザクションが、ブロッカーが非高優先度のときタイムアウトをスキップする分岐がある。何が利用者から見て高優先度になるかは今回確認していない。マニュアルの変数節にこの例外は無い。

待たない読み取りもある。既定の分離レベルは `REPEATABLE READ` で、通常の `SELECT`（一貫性読み取り）はロックを取らないので行ロックを待たない。待つのは `SELECT ... FOR UPDATE` / `FOR SHARE`、および `UPDATE` / `DELETE` である。`SERIALIZABLE` かつ `autocommit` がオフの平文 `SELECT` は `FOR SHARE` になり、待ち得る（[InnoDB Transaction Isolation Levels（8.4）](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)、[Consistent Nonlocking Reads（8.4）](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)）。ギャップロック同士は競合しない。待ちが起きるのは、挿入インテンションやレコードロック、ネクストキーロックが、既存の非互換ロックと衝突したときである。したがって120秒への延長が長く閉じたままにするのは「1行」とは限らない。`REPEATABLE READ` の範囲スキャンが押さえた隙間は、余分な待ちのあいだ挿入を拒み続ける（[InnoDB Locking（8.4）](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)）。

| 見ているもの | 50秒でも120秒でも同じか |
| --- | --- |
| ブロッカーの処理速度と、ロックを放す時刻 | 同じ。天井は持ち手を速くしない |
| デッドロック検出がオンのときの 1213 | 同じ。タイムアウトは輪に適用されない |
| メタデータロック（ALTER や `LOCK TABLES` 由来の MDL） | 同じ。管轄は `lock_wait_timeout` |
| 保持が50秒以内の待ちの成否 | 同じ。相手の解放時刻で成功する |
| 保持が50秒超120秒以内の待ちの成否 | 違う。50は1205、120は解放時に成功し得る |
| 保持が120秒超、または放置されたときの占有 | 違う。両方1205だが、待ち側は最大70秒長く接続を塞ぐ |
| 待ち側が同じトランザクションで先に取ったロック | 占有が伸びた分、第三者を止める時間も伸び得る |

## 50秒を選んだ手紙は、文書のどこにも無い

行ロックを発明したあとに必要になったのは、「輪でない待ち」を有限にするベルである。確認できた最も古いマニュアル文は MySQL 4.0/4.1 世代で、既定はすでに **50秒**である。その文は、InnoDB が見つけられないデッドロック（当時は `LOCK TABLES` や他エンジン）をタイムアウトが解く、と書いている。見つけられるデッドロックはロック表を見て自分で戻す。同じ文は、MySQL 4.0.20 と 4.1.2 以降に InnoDB が `LOCK TABLES` に気づく、とも書く。つまりこの版は「ロック表が見える範囲が広がった版」であり、タイムアウト変数が生まれた版としては書かれていない（[mysql.info InnoDB start](http://osr507doc.xinuos.com/cgi-bin/info2html?(mysql.info.gz)InnoDB%20start&lang=en)）。4.0.20 の見出し日付は **2004年5月18日**、4.1.2 は **2004年5月30日**である（[MySQL 4.1 リファレンス目次](http://marcinmazurek.com.pl/download/manual-4.1/index.html)）。2004年11月3日、フォーラム利用者が当時のマニュアルから "The default is 50 seconds." まで引用している（[MySQL Forums, 2004-11-03](https://forums.mysql.com/read.php?20,5095,5095)）。変数と既定50秒は 4.0.20 より前から文書化されていた、と読んでよい。ただし 2001年の最初の同梱ビルドのソース定数は、この調査では読んでいない。「最初から50」は「見つかった最古のマニュアルが50」であり、「2001年のソースを読んで50だった」ではない。**なぜ10でも60でもなく50なのかを説明した設計メモ、Heikki Tuuri のコメント、メーリングリストは見つかっていない。** 別の初期既定だった、という差分も無い。否定も、2001年のソースを見るまでは完了しない。

InnoDB の会社の側は、英語版 Wikipedia が次の日付を書く。1995年に Heikki Tuuri が Innobase を設立し、2000年9月に MySQL AB との協業が始まり、2001年3月に InnoDB を組み込んだ MySQL がリリースされた。2005年10月に Oracle が Innobase を買収し、2010年1月に Sun を買収し、2013年7月8日に Innobase は事業を終えて Oracle に吸収された、という記述である（[Innobase - Wikipedia](https://en.wikipedia.org/wiki/Innobase)）。1995年、2000年9月、2001年3月、2010年1月、2013年7月8日は、この調査では本人の告知や登記では再確認していない。2001年3月の MySQL の版番号も未確認のため書かない。買収そのものの日付は一次に近い。Oracle のプレスリリースは **2005年10月7日**、InnoDB は単体製品ではなく MySQL の一部として配布されていた、と発表している（[Oracle press release, 2005-10-07](https://web.archive.org/web/20181115071936/http://www.oracle.com/us/corporate/press/016679_EN)）。InnoDB がサーバの既定エンジンになったのは 5.1 ではない。公開されたばかりの MySQL 5.5 リリース候補が初めて InnoDB を既定バックエンドにした、と **2010年9月20日**の Linux.com が書き、**2010年12月15日**の 5.5 GA 告知も既定エンジンが InnoDB だと書いている（[Linux.com, 2010-09-20](https://www.linux.com/news/first-release-candidate-mysql-55-innodb-default/)、[DBTA, 2010-12-15](https://www.dbta.com/Editorial/News-Flashes/MySQL-55-Now-Generally-Available-72995.aspx)）。

途中で変わったのは、ベルの長さではなく、鳴ったときに戻す範囲である。2005年8月2日、Michael Widenius は Bug #12308 で、ロック待ちタイムアウトやデッドロックがトランザクション全体を戻すと使いにくい、直前の文を再実行する方が易しい、と起票した。同日 Heikki は、デッドロックを解くには全体を戻す必要がある、InnoDB はロックをビットマップに置き、どのビットがどの SQL 文で立ったかを覚えない、だから直前の文のロックだけを放すことはできない、と返した。2005年9月4日、Heikki は「5.0.13 で修正した。ロック待ちタイムアウトは直前の SQL 文だけを戻す。以前はトランザクション全体を戻していた」と書いた。デッドロックは全体のままである（[Bug #12308](https://bugs.mysql.com/bug.php?id=12308)）。2005年9月8日、Paul DuBois が 5.0.13 の変更履歴に載せた。古い挙動に戻す `--innodb_rollback_on_timeout` が MySQL 5.0.32 以降で使える、という文は Stack Overflow が当時の 5.0 マニュアルを引用したもので、変更履歴の原文はこの調査では見ていない（[Stack Overflow, 2010-03-08](https://stackoverflow.com/questions/2400744/innodb-lock-wait-timeout)）。8.4 のマニュアルは今も、タイムアウトで戻るのは文であり、全体を戻すには起動オプションだと書く。5.0.32 という導入版はその段落には無い。

行の鉛筆と目録カードが別になったのは **2010年3月24日**の MySQL 5.5.3 である。開いているトランザクションが終わるまで DDL を待たせ、バイナリログの順序が狂わないようにした（[MySQL 5.5.3 version reference](http://ftp.ncnu.edu.tw/Unix/Database/MySQL/doc/mysqld-version-reference/en/ch05s04s01.html)）。その待ち `lock_wait_timeout` の既定は **31536000秒（1年）**で、8.4 でも同じである。InnoDB の50秒には従わない（[MySQL 8.4 server system variables](https://dev.mysql.com/doc/refman/8.4/en/server-system-variables.html#sysvar_lock_wait_timeout)）。2013年2月28日、Daniel Nichter は「50秒は妥当だが1年は妥当ではない」と書き、実装者の Konstantin Osipov は、1年はタイムアウトの無かった 5.1 との互換のために選んだ、ほかの値にしても批判されただろう、とコメントしている。どちらも意見であり、コード上の既定が1年であることは 8.4 が事実として残している（[Percona, 2013-02-28](https://www.percona.com/blog/mysql-5-5-lock_wait_timeout-patience-is-a-virtue-and-a-locked-server/)）。2025年11月18日に起票され翌19日に Verified となった Bug #119422 は、なお1年を事実上タイムアウト無しだとして引き下げを提案している（[MySQL Bug #119422](https://bugs.mysql.com/bug.php?id=119422)）。したがって「ロック待ちを50秒より長くしたい」が ALTER や MDL だった場合、`innodb_lock_wait_timeout` を120にしても効かない。

検出そのものを切るスイッチは **2016年9月6日**の MySQL 5.7.15 で追加された `innodb_deadlock_detect` である。高競合で同じロックを大勢が待つと検出が遅くなるので、検出を切り、デッドロック時のロールバックを `innodb_lock_wait_timeout` に任せる方が効率的なことがある、とリリースノートは書く（[Changes in MySQL 5.7.15](https://docs.oracle.com/cd/E17952_01/mysql-5.7-relnotes-en/news-5-7-15.html)）。検査をやめると、本当に輪になっている二人もベルまで立ち続ける。検出オフのときのマニュアルは "transaction rollback" と書くが、通るのはタイムアウト経路である。既定の `innodb_rollback_on_timeout=OFF` のままでは、1205 の文ロールバックになると読むのが、変数節とエラー処理節を合わせた解釈である。検出オフが 1213 を出す、とは書かれていない。この組み合わせを 8.4 で実行した公式テスト結果は未確認である。

8.0 で変わったのは「ロックを見る窓」であり、50秒ではない。`INFORMATION_SCHEMA.INNODB_LOCKS` は 8.0.1 で削除され、代わりが `performance_schema.data_locks` である。古い表は、誰かが待っているロックだけを出した。`data_locks` は、誰も待っていなくても保持ロックを出す（[The data_locks Table（8.0）](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/performance-schema-data-locks-table.html)）。8.0.1 のリリース日は未確認で、GA の 8.0.11 は **2018年4月19日**である（[MySQL 8.0 FAQ](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/faqs-general.html)）。MySQL 8.4.0 LTS は **2024年4月30日**に始まる。8.4.0 で既定が変わった InnoDB 変数の公式一覧（Table 1.1）に `innodb_lock_wait_timeout` は無い。変わったのはバッファプール、アダプティブハッシュインデックス、I/O 容量、ログバッファなど別の変数である（[What Is New in MySQL 8.4](https://dev.mysql.com/doc/refman/8.4/en/mysql-nutshell.html)、[Oracle MySQL blog, 2024-11-28](https://blogs.oracle.com/mysql/auto-adapting-configuration-parameters-in-mysql)）。8.0 も 8.4 も Default Value は 50 である。コミュニティの 8.4.7 は **2025年10月21日**で、そのリリースノートを変数名で検索してもこのタイムアウトの変更はヒットしなかった（[Changes in MySQL 8.4.7](https://dev.mysql.com/doc/relnotes/mysql/8.4/en/news-8-4-7.html)）。ノート PDF（文書生成 2026年9月24日）では、サーバとしての新しい版は 8.4.11（**2026年7月28日**）で、8.4.12（**2026年8月18日**）は Docker イメージだけの重要セキュリティ修正だとノート自身が断っている（[MySQL 8.4 Release Notes PDF](https://downloads.mysql.com/docs/mysql-8.4-relnotes-en.pdf)）。調査日 2026年10月8日時点の 8.4 マニュアルの行ロック待ち既定は、なお50秒である。

公式は二つの方向を両方書く。対話的な OLTP では値を下げ、利用者へ早く返すか、更新をキューに回す。データウェアハウスの変換段のように、他の大きな INSERT や UPDATE の完了を待つバックエンドでは上げてよい（[8.4 パラメータ](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_lock_wait_timeout)）。Rick James は「50秒に当たるなら設計が悪い。このタイムアウトは、ほかの方法では捕まえられない行儀の悪いものを捕まえるためにある」と答えている（[DBA Stack Exchange](https://dba.stackexchange.com/questions/2763/set-lock-wait-timeout-in-mysql)）。2026年の二次記事は、多くの OLTP では50秒は長すぎ、5〜10秒で早く失敗させた方が問題が見える、バッチはグローバルではなくセッションで高くする、と勧める（[neverblink, 2026-09-22](https://neverblink.ai/kb/mysql-innodb-lock-wait-timeout-exceeded)）。5〜10秒は Oracle の既定でも、測定された中央値でもない。「みんなが5秒にしている」とは言えない。対比として、Ask Tom が説明する Oracle の通常の DML には、InnoDB の50秒に相当するサーバ既定タイムアウトは出てこない。待ちを切るのは `SELECT ... FOR UPDATE WAIT n` のように SQL が頼んだときである。ある 11gR1 の例で `distributed_lock_timeout` が60秒だったのは分散トランザクションの話で、50と60を兄弟の設計と結ぶ資料は無い（[Ask Tom](https://asktom.oracle.com/ords/asktom.search?tag=lock-wait-timeout)）。

## 1205は一文だけ消え、1213は取引を丸ごと消す

エラー番号の違いは、戻る範囲の違いである。**1205** はシンボル `ER_LOCK_WAIT_TIMEOUT`、SQLSTATE は汎用の **`HY000`**、メッセージは `Lock wait timeout exceeded; try restarting transaction`。InnoDB が言うのは、待ちすぎた文がロールバックされたのであり、トランザクション全体ではない、ということである（[MySQL 8.4 Error Reference、文書生成 2026-10-01](https://dev.mysql.com/doc/mysql-errors/8.4/en/server-error-reference.html#error_er_lock_wait_timeout)）。**1213** は `ER_LOCK_DEADLOCK`、SQLSTATE は **`40001`**、メッセージは `Deadlock found when trying to get lock; try restarting transaction`。デッドロックに当たったトランザクションは自動で全体が戻され、回復は「このトランザクションの操作を全部やり直す」である（[同リファレンスの 1213](https://dev.mysql.com/doc/mysql-errors/8.4/en/server-error-reference.html#error_er_lock_deadlock)）。SQLSTATE だけを見て再試行する実装は、1205 を取りこぼす。

既定の `innodb_rollback_on_timeout` は **OFF**、スコープは Global、Dynamic は **No** で、実行中の `SET` では変わらない。変更にはサーバ再起動が要る。OFF ではタイムアウト時に最後の文だけを戻す。ON ではトランザクション全体を中断して戻す（[innodb_rollback_on_timeout（8.4）](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_rollback_on_timeout)）。エラー処理の指示は分かれている。デッドロックなら全体をやり直す。ロック待ちタイムアウトなら、既定では文を再試行し、起動オプションを有効にしていれば全体を再試行する（[InnoDB Error Handling（8.4）](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)）。8.4 の `lock0wait.cc` は、タイムアウト処理が `DB_DEADLOCK` を上書きしない理由を「全体を戻すのはデッドロック側であり、今のクエリだけではない」とコメントしている。

文だけ戻ることの危険は、先行する変更が生きたまま残ることである。Percona の実験では、OFF のまま先に成功した UPDATE はタイムアウト後も残り、その後の COMMIT で表に書かれた。ON ではその UPDATE も残らなかった。実験は 2020年7月27日のもので、8.4 上の再実験ではないが、公式の「文だけ戻る」と一致する（[Percona, 2020-07-27](https://www.percona.com/blog/the-transaction-behavior-impact-of-innodb_rollback_on_timeout-in-mysql/)）。クライアントが 1205 を無視して COMMIT すると、途中までの変更が確定し得る。失敗した文だけを別の接続でやり直すと、元のトランザクションがまだ持っている変更と二重になる。接続プールへ戻す前に ROLLBACK しないと、次の借り主が開いたトランザクションとそのロックを引き継ぐ。これは「トランザクションが残る」という仕様からの推論であり、特定製品の不具合報告を引用したわけではない。`autocommit=1` なら文がトランザクションそのものなので、文のロールバックで単位は閉じる。複数文を一つの取引にまとめているときほど、1205 でも全体を ROLLBACK してから仕事の単位をやり直す方が、業務上の原子性には合う。Percona の結論は、パラメータの値にかかわらずそうすべきだ、というものである。マニュアルの「文を再試行」は、同じ開いたトランザクションの中で戻った文だけをやり直す、と読める。先の文の変更は生きているので、「全部なかったこと」にはならない。

もう一つの読み違えがある。エラー処理のページは、MySQL 層が検出する「その他のエラー」について、対応する SQL 文を戻すが、単一文のロールバックではロックは解放されない、と書く。この文は 1205 の箇条そのものではなく、その後の「その他のエラー」に付いている。1205 について安全に言えるのは、待っていた文が戻ること、トランザクションは開いたままなので先行文が取ったロックは残ること、までである。タイムアウトした文自身が待ちに入る前に取ったロックが、文のロールバックで解放されるかは、8.4 マニュアルの 1205 の箇条には書かれていない。Heikki が 2005年にデッドロック側へ残した制約は今もそこにある。ビットマップは文ごとのロックを覚えないので、輪を壊すにはトランザクションごと捨てる。タイムアウト側だけ「直前の文」にした結果、失敗した文より前に取ったロックは残る。天井を70秒延ばすと、その先行ロックが第三者を止める時間も最大70秒延び、1205 のあと OFF のまま放置される「半分だけ戻った開きっぱなし」も70秒遅く始まる。

1205 は InnoDB の行ロックと、メタデータロックの両方で出る。`lock_wait_timeout` が尽きたときもエラーは `ER_LOCK_WAIT_TIMEOUT` で、番号も SQLSTATE もメッセージも同じである（[lock_wait_timeout（8.4）](https://dev.mysql.com/doc/refman/8.4/en/server-system-variables.html#sysvar_lock_wait_timeout)）。切り分けは `performance_schema.data_lock_waits` と `metadata_locks` である。MySQL 開発者 Jakub Łopuszański は 2024年5月15日、前者を InnoDB 層のデータロック、後者をサーバ層の MDL と切り分けている（[Bug #114949](https://bugs.mysql.com/bug.php?id=114949)）。`innodb_lock_wait_timeout` は `SET_VAR` 不可、`lock_wait_timeout` は `SET_VAR` 可である。ヒントで片方だけ変えたつもりが、もう片方は変わらない。MDL のタイムアウトはロック試行ごとに別々に適用され、一つの文が複数のロックを要すると、設定秒数より長くブロックしてから 1205 を出し得る。

## 8.4.7のAuroraは、待つ人を伸ばしても持つ人を切れない

Aurora MySQL の 8.4 互換は、version 3 の上に乗った版ではない。version 2 が MySQL 5.7 互換、version 3 が MySQL 8.0 互換、version 8.4 が MySQL 8.4 互換である。`8.4.7` の `8.4` がメジャーで、`7` がマイナーである（[メジャーバージョンアップグレード](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.Updates.MajorVersionUpgrade.html)、[Aurora MySQL version 8.4](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.MySQL84.html)）。AWS は **2026年5月21日**に Aurora MySQL 8.4 の一般提供を告知し、コミュニティ MySQL 8.4.7 互換だと書いている（[AWS Database Blog, 2026-05-21](https://aws.amazon.com/blogs/database/amazon-aurora-mysql-8-4-is-now-generally-available/)）。リリースノートの 8.4 系統で確認できたのは二本で、8.4.7（2026-05-21、標準サポート終了 2027-11-30）と 8.4.8（**2026年9月3日**、コミュニティ 8.4.8 互換、標準サポート終了 2028-03-31）である（[Aurora MySQL 8.4 updates](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraMySQLReleaseNotes/AuroraMySQL.Updates.84Updates.html)、[リリースカレンダー](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraMySQLReleaseNotes/AuroraMySQL.release-calendars.html)）。

**`aurora_transaction_timeout` は Aurora MySQL 8.4.8 以上にだけある。8.4.7 のドキュメント上にはまだ無い。** 既定は **0（無効）**、単位は秒、スコープは Session と Global、動的だが新しい InnoDB トランザクションにだけ効く。対象は DML を実行する InnoDB トランザクションで、読み取り専用も含む。タイマーは最初の InnoDB 文で始まり、`BEGIN` だけでは始まらない。期限が来ると、実行中のクエリがあれば中断してトランザクションをロールバックし、接続は使える。クエリが無くアイドルなら接続を切る。実行中のクライアントエラーは `ERROR 63952 (40001)` である。ページは「設定した `aurora_transaction_timeout` より長く開いたトランザクションは、他のタイムアウト設定に関係なく終了する」と書く。XA PREPARE 済みと、write forwarding を含むトランザクションは対象外である（[Transaction timeout in Amazon Aurora MySQL](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.TransactionTimeout.html)、[Aurora MySQL 8.4.8](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraMySQLReleaseNotes/AuroraMySQL.Updates.848.html)）。切る対象が逆である。行ロック待ちは待ち側の現在の文を伸ばす。トランザクションタイムアウトは、ブロッカーを含む開いた InnoDB トランザクションを年齢で切る。8.4.8 以上で有効値が120未満なら、待ち側が120秒待つ前にブロッカーが消えることがある。既定 0 のままなら、この介入は起きない。8.4.7 でアイドルブロッカーを同じ仕組みでは切れない。

パラメータの変え方は、クラスターパラメータグループではなく、インスタンスの DB パラメータグループである。一覧の表に `innodb_lock_wait_timeout` が Modifiable **Yes**、注記 None で載っている。クラスター表側の走査では、この名前はインスタンス節の中で一度だけヒットした。別パラメータ `lock_wait_timeout` もインスタンス表にあり、こちらがメタデータロック用である（[Aurora MySQL configuration parameters](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.Reference.ParameterGroups.html)）。ただし同じページの前文は「特記なきパラメータは Aurora MySQL version 2 と 3 に有効」としており、8.4.7 向けの明示行は無い。Aurora が適用しないパラメータの抜粋にこの名前は無く、一覧は網羅ではないとページが断っている。Serverless がカスタム値を無視して自分で変えるのは `innodb_buffer_pool_size`、`innodb_purge_threads`、`table_definition_cache`、`table_open_cache` の四つで、その中に `innodb_lock_wait_timeout` は無い（[Performance and scaling for Aurora Serverless](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2.setting-capacity.html)）。コミュニティでは `SET GLOBAL` が以後の新規接続の初期値だけを変え、既存接続のセッション値は書き換わらない。`SET SESSION` はそのクライアントだけを変える。どのクライアントでも SESSION は変更できる。Apply type が dynamic か static かは、AWS のこの行には書かれていない。再起動をまたいで残す正規の場所はパラメータグループ、という読みは RDS/Aurora の一般運用と整合するが、この変数の行でその文面は確認していない。**既定が50のまま、と Aurora が明言したページは無い。** パラメータ表に既定値欄は無く、注記 None は「Aurora 固有の上書き説明が無い」と読める。コミュニティ既定50をそのまま使うのが、最も薄い仮定である。`describe-db-parameters` による 8.4.7 の Engine default と許可レンジは、この調査では取っていない。`innodb_rollback_on_timeout` が Aurora のパラメータグループにあるかも未確認である。

リーダーを増やしても、行ロックの競合は減らない。クラスターボリュームはライターもリーダーも同じで、データ変更はプライマリだけが行う。リーダーは同じボリュームに接続するが読み取りだけである。レプリカはプライマリに加えて最大15で、この説明は Serverless にも当てはまると注記がある（[Amazon Aurora DB clusters](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Overview.html)）。Serverless の説明でも、ライターがすべての DDL と DML を処理し、リーダーは `SELECT` のような読み取り専用を処理する。読み取り容量が足りなければリーダーを追加し、リーダーエンドポイントで読み取りを分散してライターの負荷を下げる（[How Aurora Serverless v2 works](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2.how-it-works.html)）。ロックを取らない一貫性読み取りはリーダーへ逃がせる。`UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` の行ロックはライターで取られる。`innodb_lock_wait_timeout` をリーダーのパラメータグループだけ変えても、ライターで待っている DML には効かない。リーダー上の `SELECT ... FOR UPDATE` が即エラーになるか、write forwarding でライターへ送られるかは、今回取得したページには手順として無い。

スケールの入力としてドキュメントが名指しするのは、ライターまたはリーダーごとの **CPU、メモリ、ネットワーク**である。接続数そのものはスケール条件として書かれていない。各 ACU は約 **2 GiB** のメモリと、対応する CPU とネットワークである。スケールは接続が開いたまま、トランザクション実行中、テーブルがロックされたままでも起き、進行中の操作を切らない（[How Aurora Serverless v2 works](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2.how-it-works.html)）。したがって120秒待ちの途中で ACU が変わっても、そのことだけでは 1205 にならない。見るメトリクスは `ServerlessDatabaseCapacity` と `ACUUtilization` で、`DatabaseConnections` と `Queries` も監視対象には挙がるが、接続数はスケールの入力とは書かれていない。行ロック待ちのイベント名は条件待ち（`synch/cond/innodb/row_lock_wait`）であり、そのあいだクエリは実行していない。AWS は「ロック待ちは CPU を使わない」とは書いていない。待ちが増えると CPU 理由で必ずスケールアップする、とは言えない。各接続はメモリを使い、メモリはスケール入力である。同じ到着率なら、天井が50秒から120秒になると同時に滞留する待ち接続は最大で2.4倍になり得る。それがメモリを押し上げればスケールアップ、またはスケールインを遅らせることはあり得る。これは計算上の推論で、AWS の測定値ではない。1セッションあたりのメモリ量はドキュメントから取っていない。`max_connections` は現在の ACU ではなく最大 ACU から換算したメモリに公式を適用した値で、スケールダウンしても接続が切れないよう一定に保つ。表では Aurora MySQL が 1 ACU で **90**、8 ACU で **1,000**、256 ACU で **6,000** である。閉じた代数式は取得した英語ページには印刷されていない。ロック待ちを120秒にしても接続枠は増えない。滞留が増えて Error 1040 に近づく方向である（[容量設定](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2.setting-capacity.html)、[Managing performance](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.Managing.Performance.html)）。

ドキュメント同士の食い違いを隠さない。8.4 は version 3 の最新と同じ Aurora 機能を持ち、例外は Fast insert だけ、と機能ページは書く。一方、Serverless の容量表とパラメータグループ族は version 3 と `aurora-mysql8.0` しか書いていない。8.4.8 のリリースノートは Serverless のスケール中の不具合修正を書いているので、8.4.8 時点ではスケール処理がエンジン内にある。8.4.7 の Serverless v2、最小 0 ACU、パラメータ族の名前は、取得した容量ページだけでは断定できない。0 ACU への自動ポーズは、利用者の接続が無い状態が続いたあとで、対象として書かれているのは Aurora MySQL 3.08 以降である。開いた待ち接続があるかぎり休止しない、という仕様は、接続がある状態の話として一次情報に載っている。

呼び出し側が先に切れる問題は、120秒化の大きい欠点である。Application Load Balancer の接続アイドルタイムアウトは、リクエスト全体の制限時間ではなく、既存接続でデータが送受信されない時間である。既定は **60秒**、有効範囲は1〜4000秒である（[LoadBalancerAttribute](https://docs.amazonaws.cn/en_us/elasticloadbalancing/latest/APIReference/API_LoadBalancerAttribute.html)）。ロック待ちのあいだアプリが1バイトも返さないと、既定では約60秒でロードバランサが接続を閉じ得る。DB の天井を120秒にすると、利用者側が切れたあとも MySQL が最大あと約60秒待ち続ける、という段差が既定値どうしで生まれる。閉じたときの HTTP ステータスが必ず 504 である、とは属性ページは書いていない。API Gateway の REST 統合タイムアウト既定は **29秒（29000ミリ秒）**で、超えると HTTP 504 になる。エッジ最適化は29秒を超えられず、引き上げもできない。Regional とプライベート REST は29秒を超えられるが、アカウントのリージョン別スロットルクォータの引き下げが必要になることがある。29秒超を許す変更は 2024年6月4日に発表された（[API Gateway quotas](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-execution-service-limits-table.html)、[What's New, 2024-06-04](https://aws.amazon.com/about-aws/whats-new/2024/06/amazon-api-gateway-integration-timeout-limit-29-seconds/)）。よくある引き上げが90秒まで、という2026年5月14日の re:Post の文は、公式クォータ表の本文には無い。マニュアルは、クライアントが先に切れても InnoDB のロック待ちが即時に中断される、とは書いていない。層が別であることから、呼び出し側が死んだあともサーバ側の待ちが天井まで残る、と読む。これは推論であり、切断時の実験記録は無い。

RDS Proxy の `ConnectionBorrowTimeout` 既定は **120秒**、API の制約は0〜300秒である。プールの接続が最大まで開いていて全部使用中のとき、空きまでプロキシが待つ秒数でもある（[RDS Proxy connections](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/rds-proxy-connections.html)）。借りたあとにその SQL 自身がさらに最大120秒ロック待ちすると、利用者から見た時間は足し算に近づく。これは段差の機構であり、実測ではない。バッチだけ `SET SESSION innodb_lock_wait_timeout=120` するのは MySQL 的には正しいが、RDS Proxy はセッション変数の `SET` を原則ピン留めする。`innodb_lock_wait_timeout` が追跡リストに含まれるかは抜粋では確認できなかった。含まれなければ、バッチの `SET` はその DB 接続をセッション終了まで専有し、多重化を壊す。初期化クエリに入れると全バックエンド接続が同じ値になり、OLTP とバッチで分ける目的と矛盾する（[Avoiding pinning](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/rds-proxy-pinning.html)）。Lambda の Timeout 既定は **3秒**、同期呼び出しの上限は **900秒**である。120秒の DB 待ちは、既定の Lambda では成立しない。関数タイムアウトを120秒以上にすると、待っているあいだ同時実行が積み上がり、課金対象の時間も伸びる（[Configure Lambda function timeout](https://docs.aws.amazon.com/lambda/latest/dg/configuration-timeout.html)）。毎秒 R 件が120秒滞留すると同時実行はおよそ R×120、50秒ならおよそ R×50、というのはリトルの法則による説明用の計算であり、実測ではない。

フェイルオーバーとの長さの比較も、120秒を不利にする。レプリカがあるときの復旧は通常60秒未満、しばしば30秒未満で、そのあいだ読み書きは例外で失敗する（[High availability for Amazon Aurora](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.AuroraHighAvailability.html)）。50秒待ちでも重なり得る。120秒にすると重なる時間の上限が伸び、待ちの途中の失敗は 1205 ではなく接続エラーとしてアプリに見える。これは時間の長さの比較からの推論で、「120秒にするとフェイルオーバーが失敗する」ではない。レプリカが無く新しいプライマリを作る場合、復旧は通常10分未満なので、120秒待ちはこちらの復旧より短いこともある。フェイルオーバー瞬間にカウントがリセットされるかは未記載である。

長いトランザクションが undo を持ち続ける時間も、このパラメータは縮めない。履歴リストが伸びるとクエリとシャットダウンが遅くなり、Aurora では全インスタンスが同じストレージボリュームを使うので、ガベージコレクションはインスタンス単位ではなくクラスター全体の問題になる。ハンドブックは、数分以上開いているトランザクションを調査対象とし、`trx_rseg_history_len` が数万だと遅れ、数百万から数千万は危険だ、と書く。この推奨の本体は InnoDB 全般にも当てはまると断っている（[Transaction management and autocommit](https://docs.aws.amazon.com/whitepapers/latest/amazon-aurora-mysql-db-admin-handbook/transaction-management-and-autocommit.html)、[history list length](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/proactive-insights.history-list.html)）。単発の120秒待ちそのものが履歴リストを危険域にする、とは言えない。問題は、ブロッカーが何分も開いたままであることと、その後ろでロックや読み取りビューを持ったセッションが鎖になることである。まだ何も変更していない純粋な待ちだけなら、そのセッション自身の undo は小さい。ドキュメントはこの切り分けを `innodb_lock_wait_timeout` の言葉では書いていない。8.4.7 で purge を直接守るレバーは無く、8.4.8 以上の `aurora_transaction_timeout` がそれにあたる。

## 120秒が通るのは、測ったバッチの裾だけである

利益の機構は一つに限られる。正当な処理が行ロックを50秒より長く、120秒以内に必ず放すなら、待たされている側の 1205 は減り、解放の時刻に成功する。マニュアルが上げてよいと書くのは、ウェアハウスの変換段が他の大きな INSERT や UPDATE の完了を待つ場合である。AWS の行ロック待ちページの例は、`SELECT ... FOR UPDATE` が `User sleep` で82秒生きているトランザクションにブロックされている。この数字を機構に当てはめると、天井50では待ち側は1205、天井120では82秒目に成功し得る。相手が82秒で本当に終わるなら、オペレータが気づく窓も50秒より広い。相手が眠ったままなら、その窓は被害の延長でもある。これは例の数字の当てはめであり、AWS が50と120を測った結果ではない（[synch/cond/innodb/row_lock_wait](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/ams-waits.row-lock-wait.html)）。スコープが Session なので、バッチ接続だけ `SET SESSION innodb_lock_wait_timeout = 120` とでき、その後の接続へグローバル値は染み出さない。グローバル120は、マニュアルの「OLTP は下げる」と逆向きである。

不利益の機構は、相手が放さないときに同じ70秒が裏返ることである。利用者は最大120秒待ってから失敗する。そのあいだプールの接続、Lambda の実行時間、呼び出し側がすでに切ったあとのサーバ側セッションが塞がる。待ち側が先に取ったロックと、ネクストキーが閉じた隙間は、余分な時間のあいだ他者を止める。同じロックに多数がぶら下がると、全員がほぼ同時に天井へ達する。待たずに再試行すると、同じロックへ再び同じ本数が入る。120秒は1回あたりの占有が長く、50秒は失敗と再試行の回数が多い。どちらも、ブロック側を放置したままでは悪化する。解放の瞬間に待ち側が一斉に走り出すことは機構上あり得るが、測定は見つかっていない。1205 の件数だけを見ていると、50秒で切れていた待ちが数えられなくなり、「改善した」ように見える。`Innodb_row_lock_time_max` の単位はミリ秒なので、理論上50000までだった山が120000まで許される。コミット忘れや、トランザクションの途中で入力を待つ実装は、50秒ならその時点で待ち側が例外を上げる。120秒では同じ欠陥が70秒長く本番の接続を握る。Baron Schwartz が問題視したのは、開いたまま何もしない接続と、途中で COMMIT しないバッチループである（[Percona, 2011](https://www.percona.com/blog/how-to-debug-long-running-transactions-in-mysql/)）。Percona Server の OLTP 向け設定例（2026年10月5日）は、このタイムアウトを50のままにし、`innodb_rollback_on_timeout` を ON にしている。これは「50を維持した公開設定例」であり、120を禁止する実験結果ではない。

説明用の算術を、測定と取り違えないための数字だけ置く。プール200本が同じロックに一斉に並び、アプリは1205のあと接続を返す、と仮定する。ブロック側が80秒で COMMIT するなら、天井50は50秒で1205、天井120は80秒目に成功する。成功は増えるが、200本が80秒塞がる。ブロック側が10分止まったままなら、両方1205で、120は1本あたり70秒、200本合計で14000接続秒長く塞ぐ。プールが200で頭打ちなら、その70秒のあいだ新しい OLTP は接続を借りられない。200、80秒、10分、14000接続秒は実システムの観測ではない。

120秒が筋の通るのは、次をすべて満たすときである。正当なロック保持を測っており、その裾が50秒より長く120秒より短い。この調査はその測定を持っていないので、持つまでこのクラスタで「妥当」とは決められない。上げるのはバッチまたはバックエンドのセッションだけで、OLTP の接続は50以下のままである。公式は OLTP で下げることさえ勧めている。そのバッチを呼ぶ経路のタイムアウトがすべて120秒より長い。ALB を通すなら無通信60秒の既定を延ばすか、待っているあいだバイトを返す。API Gateway 既定29秒の同期 API の奥では、120秒は成立しない。プールに空きがあり、待ち本数かける最大120秒でも借り出しが枯れない。RDS Proxy を使うなら、借り出しタイムアウトとピン留めをセットで見る。アプリは1205でトランザクション全体を ROLLBACK し、仕事の単位ごと、時刻をばらしてやり直す。ジッタの秒数を裏づける測定は無く、マニュアルが義務付けているわけでもない。

害になるのは、一つでも強いときである。対話 API のグローバル値を上げて1205を減らしたいだけである。呼び出し側が60秒以下である。プールが上限付近である。アイドルのままのトランザクションや COMMIT 漏れがすでに見えている。`innodb_deadlock_detect` をオフにしている。最後の場合、本当の輪の解消まで120秒になり得る。グローバルに上げるより、セッションで分ける方が、公式の「OLTP は下げ、バックエンドは上げる」と、実務の「1205を隠すな」の両方に合う。`SET GLOBAL` は後続の新規接続にだけ効くので、上げたつもりが既存の OLTP 接続にはまだ50が残る、という時間差も起きる。

見るべきは1205の件数だけではない。`performance_schema.data_locks` は、保持中のロックと、ブロックされて待っている要求の両方を出す。`performance_schema.data_lock_waits` は、要求側の `REQUESTING_ENGINE_LOCK_ID` と、それを止めている `BLOCKING_ENGINE_LOCK_ID` の組である。`information_schema.innodb_trx` の `TRX_STATE` は、待っていなければ `RUNNING`、行ロック待ちなら `LOCK WAIT`、ほかに `ROLLING BACK` と `COMMITTING` がある。`trx_started` からの秒数が、ブロッカーの年齢である。`sys.innodb_lock_waits` は `wait_age_secs`、待ち側の `waiting_query`、ブロック側の `blocking_query` を要約し、発行セッションがアイドルになると `blocking_query` は NULL になる（[sys.innodb_lock_waits（8.4）](https://dev.mysql.com/doc/refman/8.4/en/sys-innodb-lock-waits.html)、[トランザクションとロック情報（8.4）](https://dev.mysql.com/doc/refman/8.4/en/innodb-information-schema-transactions.html)）。三つの表は瞬間の内部状態で、互いに一貫している保証は無い。`data_lock_waits` の blocking id が `data_locks` に無い行は、マニュアルが予告している競合条件である。8.4 で `information_schema.INNODB_LOCKS` と `INNODB_LOCK_WAITS` を見る監視は、8.0 で既に後継へ移った前提で動かない。

ステータス変数はグローバルで、時間の単位はミリ秒である。`Innodb_row_lock_current_waits` は今待っている数、`Innodb_row_lock_waits` は待ちが発生した回数、`Innodb_row_lock_time` は取得に費やした時間の合計、`_avg` は平均、`_max` は最大である（[Server Status Variables（8.4）](https://dev.mysql.com/doc/refman/8.4/en/server-status-variables.html#statvar_Innodb_row_lock_time)）。ソースは、待ちスロットに入った行ロックの停止時間を足しているので、待たなかった即時取得は入らない、と読める。これはソース解釈である。`_max` が起動以降の高水位か、`FLUSH STATUS` で戻るかは、定義文には無い。Performance Insights の待ちイベント `synch/cond/innodb/row_lock_wait` は、あるセッションが更新用に行をロックし、別セッションが同じ行を更新しようとすると起きる。AWS の解説ページがサポート対象に書いているのは Aurora MySQL version 3 だけである。8.4 を含める文は確認していない。手順の型（Performance Insights、タイムアウト値の確認、`SHOW ENGINE INNODB STATUS`、idle か active か、`data_lock_waits`）は 8.0 系の InnoDB と同じだが、ページの版注記を 8.4 に読み替える公式更新は無い。`row_lock_wait_cond` と `aurora_lock_thread_slot_futex` の詳細ページは version 2 の注記のままなので、8.4 の根拠に使わない。メタデータロック待ちは別イベント `synch/cond/sql/MDL_context::COND_wait_status` である（[Aurora MySQL wait events](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.Reference.Waitevents.html)）。

デッドロック側のカウンタを、パラメータ値と混同しない。Performance Insights の `innodb_lock_wait_timeout` は、デッドロック節ではロック待ちタイムアウトが起きた回数の並びにあり、設定秒数そのものではない。天井を120にすると、このカウンタの増え方は遅くなる方向であり、ブロッカーの保持時間は測れない。対になるのは `innodb_deadlocks` と CloudWatch の `Deadlocks` である。`SHOW ENGINE INNODB STATUS` の `LATEST DETECTED DEADLOCK` は、再起動以降の直近1件である。`innodb_print_all_deadlocks` は DB クラスターパラメータで、ON にするとエラーログへ全件出る、とデッドロック節は書く。8.4 のパラメータ表の行としては、この調査では見ていない（[Minimizing and troubleshooting Aurora MySQL deadlocks](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.BestPractices.FeatureRecommendations.html)）。履歴リストは CloudWatch / Performance Insights の `RollbackSegmentHistoryListLength` を優先する。これは削除マーク付きレコードを持つコミット済みトランザクションの undo で、`trx_rseg_history_len` と同じ値だと AWS は書く。長いトランザクションの特定は `innodb_trx` と `processlist` の結合で、リードレプリカ上の長い読み取りも見ること、と履歴リストのページは注記する。8.4.8 以上なら、状態変数 `Aurora_transaction_timeouts` がトランザクションタイムアウトの回数である。実行中のタイムアウトだけが performance_schema の対応エラーを増やし、アイドル切断は増やさない。8.4.7 ではこの変数は手順に入れられない。

変更の前後で並べるのは、1205 の件数、`Innodb_row_lock_time` の増分、`Innodb_row_lock_time_max`、`Innodb_row_lock_current_waits`、Performance Insights の行ロック待ちの DB ロード、履歴リスト長、`ServerlessDatabaseCapacity`、`ACUUtilization`、`DatabaseConnections`、アプリのプール借り出し失敗、ALB と API Gateway の 5xx である。1205 だけ減ってプール失敗や 5xx が増えるなら、タイムアウトをデータベースの奥へずらしただけである。ブロック側が `Sleep` や `User sleep` で年齢が数十秒を超えるなら、天井を上げる前に、そのトランザクションを終わらせるか、アプリの COMMIT 漏れを直す方が先である。AWS は、アイドルなブロック側は切る対象になり得るが、長いロールバックがあり得る、と書く。ピーク中に無差別に切ると、待ちとは別の被害になる。切るコマンドの手順は、ここでは書かない。

今誰が誰を止めているかの見方は、次の読み取りである。本番で重いなら間隔を空け、行数を限る。

```sql
SELECT r.trx_mysql_thread_id AS waiting_thread,
       r.trx_started AS waiting_started,
       r.trx_query AS waiting_query,
       b.trx_mysql_thread_id AS blocking_thread,
       TIMESTAMPDIFF(SECOND, b.trx_started, NOW()) AS blocking_age_sec,
       b.trx_state AS blocking_state,
       b.trx_rows_locked,
       b.trx_rows_modified,
       b.trx_query AS blocking_query
FROM performance_schema.data_lock_waits w
JOIN information_schema.innodb_trx r
  ON r.trx_id = w.REQUESTING_ENGINE_TRANSACTION_ID
JOIN information_schema.innodb_trx b
  ON b.trx_id = w.BLOCKING_ENGINE_TRANSACTION_ID;
```

`blocking_age_sec` はブロッカーが開き続けている秒数、`blocking_state` が `LOCK WAIT` ならその人自身も誰かを待っている。`trx_query` が空で状態が sleep なら、実行中の SQL は無く、開いたまま止まっている。行ロック待ちの時間カウンタは `SHOW GLOBAL STATUS` の `Innodb_row_lock_current_waits`、`Innodb_row_lock_time`、`Innodb_row_lock_time_avg`、`Innodb_row_lock_time_max`、`Innodb_row_lock_waits` で、時間はミリ秒である。Performance Schema のロック計器が Aurora で既定有効かは未確認である。AWS の例は `data_lock_waits` を直接参照している。8.4.8 のリリースノートが同表へのクエリに言及しているのは 8.4.8 であり、8.4.7 での同表の存在はリリースノート上は未確認である。コミュニティ 8.4 の機能としては 8.0 からある表である。

## Conclusion

50秒から120秒への変更は、ロック競合の治療ではなく、失敗が届く場所の移動である。正当な保持が50秒と120秒のあいだにあるときだけ成功が増え、その帯をこの調査は測っていない。保持がそれより長いとき、および ALB の60秒や API Gateway の29秒が先に切れるときは、成功は増えず、孤児になった待ちと、先行ロックの占有だけが最大70秒延びる。8.4 の既定見直しがこの変数を動かさなかったのは、50秒がスループットのつまみではなく、輪でない待ちの尻ぬぐいとして20年以上文書に残ってきたからである。なぜ50なのかの手紙は、今も無い。

8.4.7 に欠けているのは、待ち人のベルではなく、持ち手の寿命を切るレバーである。それは Aurora 8.4.8 の `aurora_transaction_timeout`（既定は無効）として初めてドキュメントに現れ、行ロック待ちの120秒とは切る対象が逆である。リーダー追加も ACU の CPU スケールも、ライター上の行ロックの列を短くしない。グローバルに上げて 1205 を消す前に、セッションを分け、呼び出し側のタイムアウトをデータベースより長くし、`data_lock_waits` でブロッカーの年齢を見る。1205 が減って `Innodb_row_lock_time_max` と履歴リストとプールの借り出し失敗が増えているなら、ベルは遅れたのであり、鉛筆は戻っていない。
